1. Overview

The app helps someone plan and track a path into cybersecurity. It is a single Flask process that renders HTML with Jinja2 and stores everything in one SQLite file. The two core backend domains both read and write SQLite:

  • Roadmap (planning): the courses, certifications, labs, books and projects a user wants to do, with type, platform, skill tags, difficulty, priority and status (models/roadmap.py, table roadmap_items).
  • Progress (tracking): the study sessions logged against those items, with completion %, how hard it felt, minutes spent and notes; logging 100% completes the item (models/progress.py, table progress_logs).

Around them I added user accounts with login security, a career assessment (nine fields, seven questions each), a recommended phase-by-phase timeline per field shown as the home page, a stats page (study calendar, streaks, weekly and per-skill charts), a Projects page that links a public GitHub profile and turns its repositories into roadmap projects, YouTube recommendations for weak skills, and a personal data export.

2. Software development life cycle

Model: iterative and incremental

I built the app in short daily increments. Each increment had one goal (a domain, a feature or a documentation piece), was implemented, tested and committed the same day, and was checked against the assignment brief before I planned the next one. The plan lived in a status note that I updated after every session, and decisions with lasting impact went into ADR.md as they were made. I chose this over a waterfall plan because the requirements changed as I went: accounts and security, the assessment, the timeline and the redesign all came from reviewing the previous increment.

Where I followed the plan, and where I deviated

  • Followed: one increment a day, pushed the same day; tests written for every new piece of logic; ADRs written when the decision was made, not at the end.
  • Missed day: nothing was done on 29 Sep. I shifted the plan by one day and cut features instead of cramming them in: an AI FAQ assistant, two-factor login, a certification tracker, item write-ups and target dates on items.
  • Scope grew well beyond two domains. I kept it under control with an explicit cut list and by giving every new feature its own tests and its own commits.
  • Tests came after the first features (26 Sep), not test-first. Writing them found a real ordering bug: two logs saved in the same second came back in random order, fixed with id DESC as a tiebreaker.
  • Branching: until 30 Sep I committed straight to main. From 1 Oct every change went through its own branch (feature/timeline, feature/export, fix/change-field, feature/stats, feature/github, docs/…) merged with git merge --no-ff, so each one stays visible in the history.
  • Two redesigns: the original dark "terminal" look (25–27 Sep) was replaced on 30 Sep by a light design based on a mockup I made, which also changed the home page into the timeline.

3. Architecture

Figure 1 shows how a request moves through the app; the main design choices are:

  • Single process, single file. python app.py binds to 0.0.0.0:$PORT. db.py keeps one SQLite connection for the process (Singleton) with row_factory = sqlite3.Row and PRAGMA foreign_keys = ON. init_db() runs at every start and is idempotent; _migrate() adds columns that were introduced later. No Dockerfile, CI or external database is needed, as the deployment contract requires.
  • Layers. Routes in app.py stay thin: read the request, check ownership, call a model or service, render. models/ holds the SQL, one module per domain, every query parameterised and filtered by the logged-in user. services/ holds logic that isn't SQL (scoring, timeline planning, streaks and charts, export) as pure functions that take today as a parameter, so they are tested with fixed dates.
  • Domains stay independent. No model imports another; where a page needs several domains, a route or service combines them. The roadmap/progress seam is the item_id foreign key (ADR 2).
  • Data separate from logic. The question bank and the timeline content are plain Python data, passed into Questionnaire and TimelinePlanner in app.py.
  • Patterns and SOLID. Singleton (_DatabaseManager), Facade (RecommendationService and GitHubService hide the YouTube and GitHub APIs), Decorator (login_required, admin_required). Single responsibility: routes, SQL and logic live in different layers. Open/closed: nav links, icons, export formats and level thresholds are data, so adding one is a new entry, not a code change. Dependency inversion: the scoring and planning code receive their data, and GitHubService its HTTP call and clock, instead of importing them, so the tests pass in small fake data and canned GitHub responses.
  • Almost no JavaScript. Menus are HTML <details> elements and charts are SVG drawn from coordinates computed in Python. The only scripts are a few inline attributes (delete confirmations, auto-submitting filters, a slider label).

4. Database schema

  • Ownership. roadmap_items, login_events and assessments belong to a user through user_id. progress_logs has no user_id: it belongs to a user through its item, so any progress query not already behind an owner-checked item joins roadmap_items (ADR 3).
  • Cascades. Deleting an account removes its items, their logs, its login history and its assessments in one statement, which is what self-service account deletion relies on.
  • rate_events is deliberately unlinked. It counts failed logins and sign-ups against the username and IP that were typed in, which may not belong to any account.
  • Other choices. Assessment answers are stored as JSON ({question_id: option}) and scores are recomputed from them. The chosen career path is two columns on users (path_field, path_level). A linked GitHub profile is one nullable column, github_username; no token is stored. Indexes cover the per-user lookups and the rate-limit window query.

5. README and testing

README.md in the repository explains every page, the quick start (python -m venv .venv, pip install -r requirements.txt, cp .env.example .env, python app.py), all environment variables (PORT, SECRET_KEY, DATA_DIR, YOUTUBE_API_KEY, ADMIN_USERNAME/ADMIN_PASSWORD, FLASK_DEBUG), the project structure, the architecture with a schema diagram, the security measures and the branching workflow.

Tests: 273 pytest tests, 100 % line coverage on models/, ui/ and the five logic services (assessment, timelines, export, stats, GitHub). 106 of them run against a throwaway SQLite file, and the suite includes security cases: another user's ids, SQL injection payloads, lockout windows and spreadsheet-formula injection in the CSV export. The GitHub service is tested with canned API responses through its injected HTTP call, including hostile usernames and links, so no test touches the network. Routes and templates are checked by hand, and the YouTube wrapper is not unit-tested because that would mean mocking Google's API rather than testing my code (ADR 4).
